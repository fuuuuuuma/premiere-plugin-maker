## 症状

fps を調べる関数が、調べられなかったときも `fps: 30, timebase: 30` を返していた。その結果、次のようなことが起きた。

- テロップの整列で、許容の幅を「何フレーム」で数えるため、60fps なのに実質 2 倍の幅で動いた。
- シーケンスの概要が、60fps のシーケンスを 30fps と表示した。
- XML から音声の並びを読む処理が、`<rate>` が無いと黙って 30fps で進めた。

## 原因

「検出失敗」を既定値で埋めて、成功と同じ形で返す設計だった。失敗を知らせる印（`detected` というフラグ）は付けてあったが、印を見るかどうかは呼び出し元に任されていて、見ない呼び出し元が事故った。フラグは、全員が見る前提でしか効かない。

## 直し方

1. 検出関数は、未検出のとき `fps: NaN, timebase: null, ntsc: null` を返す。数として使うと計算が壊れて目立つ形にする。
2. 整列は、未検出なら実行せずに止める。概要は `fps: null` を返す。カットは、未検出なら最小無音長を送らない。
3. XML の音声の並びを読む処理は、`<rate>` が不明ならエラーで止める。
4. fps の値を使う箇所を全部洗い、他にも 30 の既定値が無いか grep で確かめる。
5. Python では `bool` が `int` の仲間なので、`True` を timebase として受け取らないよう、`bool` を除外する。

## 再発防止

- 29.97・30・59.94・60・120fps のそれぞれについて、「未検出」「正しく検出」「誤って 30 と検出」の組み合わせを試すテストを置く（fps 保持のテスト）。
- 「検出失敗は NaN・null・エラーで下流へ伝える」を、新しい関数を足すときの決まりにする。
- フラグを足して済ませず、戻り値の使い道を全部見る。
