## 症状

更新の zip を別のフォルダに展開すると、恒久的に 403 か「未接続」になる。AI から操作するためのアダプタは、`GET /ping` の 99.3% が 403（記録では 403 が 13,310 回、200 が 94 回）なのに、パネルだけは普通に動くので、誰も気づかない。

## 原因

トークンのファイル（`server/ready`）は、パネルと対になった、フォルダごとのものだった。アダプタは、自分の隣の `ready` を読む設計だったが、Claude Code に登録されたアダプタはリポジトリから起動され、稼働中のサーバーは、配布 zip を展開した別のフォルダにいた。隣の `ready` は古いトークンのまま残っていた。なお `ready` は、生のトークンでなく JSON。

壊れているのは「AI から操作する経路」だけなので、その経路を使わない日は、誰も困らなかった。

## 直し方

1. サーバーが、ポートの bind に成功したあとで、マシンに 1 つだけの場所（`<APP_SUPPORT>/server.json`）に `token` と `serverDir` を書く。
2. クライアントは、「環境変数 → `server.json` → 隣の `ready`」の順で解決する。診断にも `X-CutSRT-Token` を付ける。
3. パネルの側のフォルダ単位のペアリング（差し替えのときの誤接続の防止）は変えない。外すと別の退行が戻る。
4. 更新版は、新しいフォルダで `install.command` を再実行し、UXP Developer Tool で Remove → Add → Load をやり直す。

## 再発防止

- 接続の事前確認（プリフライト）を置く。403 のメッセージには、「見ている場所」と「稼働中の場所」の両方を名指しする。単に「HTTP 403」「パネルを再読み込みしてください」では、落ちているのか別のフォルダなのかが切り分けられない。
- 認証情報は、フォルダ単位でなく、マシンに 1 つの既知の場所へ集約する。フォルダ単位の認証は、差し替えでずれる前提にする。
- 2 回再発した（2026-07-15、2026-07-18）。07-18 の診断は推定。
