## 症状

- ブラウザが `ERR_FAILED` になる。`OPTIONS` は 204 なのに `GET` が失敗する。
- 別のツールのブリッジと 8788 番のポートを取り合い、`forbidden_origin` になる。
- プロキシが立ち上がらず、20 秒待ってから諦める。

## 原因

- 認証のヘッダ名が、サーバー側とクライアント側で違った（`X-AssetScout-Token` と `Authorization: Bearer`）。
- 後から起動したサーバーが `EADDRINUSE`（ポートがすでに使われている）を「自分が動いている」と解釈して終了コード 0 で終わった。実際は、別のコンポーネントがそのポートを握っていた。
- そのポートの持ち主は 404 を返すので、「生きていない」と見なされ、20 秒待たされた。

## 直し方

1. ヘッダ名をそろえる。
2. ブリッジは `/pair` で `app: "<識別子>"` と名乗る。クライアントは、候補のポートを順に叩き、名乗りが一致したものだけを採用する。
3. すでに生きているプロキシがあれば、それを共用する（取り合わない）。待ち時間が 20 秒から 0 秒になった。

## 再発防止

- 2 つのファイルに別々に書いた取り決め（ヘッダ名・許可するオリジン・ポート候補・名乗り・版・エンドポイントの有無）は、機械で照合するテストにする。わざと壊して、失敗することも確かめる。
- 手で組んだリクエストの成功は、実際のクライアントの検証にならない。固定のポートでなく、名乗りで相手を同定する。
