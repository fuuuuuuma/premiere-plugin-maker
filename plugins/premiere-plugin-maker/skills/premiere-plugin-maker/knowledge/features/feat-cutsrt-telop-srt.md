## 何をする機能か

シーケンスの音声から、画面に出す字幕（テロップ）の SRT ファイルを作ります。1 行の文字数の上限（既定は 25 字）に収まるよう、意味の切れ目で改行し、時刻を付けます。できた SRT はプロジェクトに読み込みます。必要に応じて訳（二か国語）も付けます。

## 作り方

流れは次の 4 段です。

1. 音声の取り出し。XML から、有効な全音声トラックを足し合わせた 1 本の音声を作る（対談では片方のマイクだけだと、もう一人の発話が落ちるため）。
2. 文字起こし。Mac は mlx-whisper（GPU）、それ以外は faster-whisper。語の時刻付きで取り、結果は再利用できるようキャッシュする。
3. 意味で区切る改行。長い本文を小さなかたまりに分け、AI に「どこで改行するか」だけを答えさせる。
4. 組み立てと検査。時刻を割り当てて SRT を書き、文字数・文頭の禁止・時間の重なりなどを機械で検査する。

### AI には改行の位置だけを任せる

初期の設計では、AI が返した文字列をそのまま使っていました。ところが、禁止している句読点が残る、固有名詞の表記が直らない、という問題が出ました。AI の出力を「元の文字起こしと一致するか」で検査して合わなければ捨てる仕組みが、AI による記号の除去や固有名詞の修正まで全部捨てていたのが原因です。

そこで役割を分け直しました。

- AI の出力からは改行の位置だけを取り出す。
- 文字そのものは、辞書の置換を当てた元の文字起こしから復元する（これを「原文投影」と呼ぶ）。
- 禁止している句読点（「、」「。」「！」）の除去や辞書の置換は、AI ではなく決まったコードで保存の直前に必ず行う。
- 最後に機械の検査（文字数超過、文頭に来てはいけない文字、0 秒の字幕、時間の重なり）を通し、残りが 0 件になってから成功とする。

守りたい表記の規則は AI のお願いではなく、決まったコードと最後の関門で守る、という方針です。

### AI が失敗しても完走する（縮退のはしご）

改行の AI が 1 つのかたまりで失敗するたびにジョブ全体を落とすと、数分かけた文字起こしが無駄になります。そこで段を作りました。

1. かたまり全体を 2 回までやり直す。
2. 通らなければ、より細かい字数（300 字、120 字）に割り直して個別に試す。
3. それでも通らないかたまりだけ、機械的な改行（文字数と禁則による分割）にする。

外部の AI を呼ぶ回数には上限（12 回）を付けました。外部の AI は 1 回に 10〜30 秒かかるため、上限が無いと体感で固まります。機械改行まで落ちたときは、ログと結果カードで「品質が下がった」ことを必ず利用者に知らせます。完全にローカルで動かす設定では、外部の AI へは一切フォールバックしません。

### ローカルのモデル

外部の AI を使わない完全ローカルの経路には、小さな言語モデルを使います。同じ実データ（約 2,800 字の文字起こし）で比べた結果、Qwen3-4B-Instruct の 4bit 版が 54.6 秒で、旧既定の 7B 版（140.1 秒）の約 2.6 倍の速さでした。文頭の禁止文字や原文投影の破棄数も 0 件でした。「考える」タイプの新しい小型モデルは、遅くて投影の破棄が多く、この用途には向きませんでした。配布先でモデルが 0 台のときは、「ローカルモデルを準備する」ボタンで取得できます。

## 使った API と道具

- `ProjectConverter.exportAsFinalCutProXML`（音声の配置を読む）、`project.importFiles`（SRT をプロジェクトへ）。テロップ本文を読み戻すときは `exportAsOpenTimelineIO`（Source Text が複合型で直接読めないため）。
- 文字起こし: mlx-whisper または faster-whisper。時刻の割り当ては、全体の文字列を照合する方式（`difflib`）で、辞書の追加が無くても時刻がずれない。
- 改行: Claude・Codex などの CLI、またはローカルの mlx-lm。
- 補助: ffmpeg、辞書（`feat-cutsrt-dictionary`）。

## つまずきと直し方

- 長い指示を引数で渡すと、Windows で途中で切れる: npm で入れた `claude.cmd` は `cmd.exe` を経由し、引数の中の改行で文が切れる。改行工程の指示は 1 万 5 千字を超えるため、1 行目だけが届き、「LLM の改行出力が原文と一致しません」で失敗した。長い指示は標準入力かファイルで渡す。
- 初回だけ改行が粗い、歌詞や雑音が字幕に混ざる: AI エンジンの初回起動が遅れる、BGM の歌詞を拾う。診断値を毎回出し、初回の条件を明記した。
- 同じ失敗を繰り返す: ローカル LLM が温度 0 で同じ入力を再試行していた。再試行では入力を半分に割る。
- 投影に失敗したかたまりを未分割のまま再分割へ渡し、ローカル LLM の呼び出しが 3 倍以上に増えて「固まる」: 失敗したかたまりを先に分割してから渡す。
- 時間の内訳に出ない約 17 秒: 辞書の語義を AI で作る処理が数えられていなかった。転写と並行にして 0 秒にした。
- 「速度変更またはタイムリマップ」と誤判定: フレームレートの検出失敗が黙って 30 に落ちていた（`feat-cutsrt-cut` を参照）。処理が実際に使ったフレームレートをログに毎回出すと切り分けられる。
- ジョブの失敗表示が 3 回重なる: ジョブのエラー応答を通信の例外に変えてしまい、ポーリングが再試行していた。ジョブの失敗は通信の失敗と別の経路で扱う。
- 範囲指定（インからアウトまで）で字幕 0 件の SRT が成功扱いになる: 0 件は失敗にする。
- 画像の挿入位置が字幕の区切りとずれる: 画像の時刻は文字起こしの区切り、字幕の境界は SRT の区切りで、境界が二重に定義されていた。配置時は、時刻を含む字幕クリップの開始・終了の `TickTime` をそのまま使い、近い編集点に吸着させる。
- SRT をキャプショントラックとして自動で置く API は無い（確認の結果、UXP の公式リファレンスにない）。SRT はプロジェクトへ読み込むところまでで、置く操作は利用者か、MOGRT・グラフィックのクリップ経由になる。

## 結果と今の状態

Mac の実機で、テロップ生成の一連が動いています。翻訳（AI の一括処理）は、「部分的な成果物を作らない、前回の出力を壊さない、本体の成功を巻き込まない」を守るようにしてあります。Windows では、改行工程の標準入力化など数件の直しの後に動いたとの報告があります。「SRT が後半しか取れない」という Windows の報告は、Mac では再現せず、原因は未確定のままです。
