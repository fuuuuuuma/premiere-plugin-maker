## 何をする機能か

Premiere で動画を書き出したら、手で送らなくても、指定した送り先へ自動で送ります。送り先は、Google Drive、ギガファイル便、Frame.io、IRERU（作者が運用する動画の受け渡しサービス）、YouTube（手動の「限定公開で送る」）です。送ったあとはリンクを出し、必要なら通知します。

## 作り方

1. 見張り: パネルで「書き出し先」のフォルダを決める。サーバーがそのフォルダを監視し、新しいファイルの大きさが 8 秒間変わらなければ「書き出しが終わった」と見なす。
2. 送り先: チェックの付いた送り先へ、順に送る。送り先ごとに、送り先の設定が正しいかをその場で検査する。
3. 状態: すべての経路が、必ず「完了・失敗・同期待ち・設置済み」のどれかに落ちる。送信中のまま止まったり、偽の完了になったりしてはいけない。この性質をテストで固定した。
4. 認証の情報: 外部サービスのトークンは、リポジトリの外の、本人だけが読める権限のファイル（アプリ用のデータフォルダ）に分けて保存する。パネルへ返す状態の応答には、トークンを含めない。鍵の値やアカウントの情報は、ログにも記録にも出さない。

### 送り先ごとの作り

- Google Drive: 最初は Drive for desktop の同期フォルダへコピーし、拡張属性（`com.google.drivefs.item-id#S`）からリンクを作った。後に、Google の OAuth で接続し、選んだアカウントのマイドライブへ直接アップロードする方式を足した。「リンクを知っている人は閲覧可」の共有設定とリンクの発行までを行う。大きなファイルは 8MiB ずつ送り、通信が切れたら同じセッションの受信位置を確かめて再開する。共有設定だけ失敗したときは「共有設定待ち」と表示し、すでに入れた動画を再利用してリンクの発行だけ再試行する。
- ギガファイル便: 公式の API が見当たらなかったため、サービス自身の Web 用アップローダーの通信手順（トップページでサーバーを取得し、`upload_chunk.php` へ分割して送る）を読んで再現した。
- Frame.io: Adobe の認証（認可コード方式と PKCE）でログインし、現行の API で送り先のフォルダを選び、分割アップロードと共有リンクを作る。ログインの戻り先は、手元のサーバーが受ける。
- IRERU: 個人用のトークンで、動画を送って受け渡し用のリンクを得る。
- YouTube: Google の OAuth で接続し、チャンネルを選び、手動の操作で「限定公開」で送る。公開の操作は人が行う前提で、自動の公開はしない。

## 使った API と道具

- サーバー側: Python の標準 HTTP クライアント、ファイル監視（大きさの安定を見る）、各サービスの REST API。
- パネル側: `fetch`、`localStorage`（設定）、フォルダ選択ダイアログ。
- 秘密の置き場: Mac のキーチェーン、Windows の DPAPI を使う部品（`keychain` 部品を参照）。

## つまずきと直し方

### 規約と費用の注意（外部サービス全般）

- 外部のサービスを自動で操作する機能は、そのサービスの利用規約に従って作る。公式の API があるものは API を使い、無いものは、規約が許す範囲の手順だけを再現する。
- ギガファイル便は、利用規約の中で並列の大量アップロードを控えるよう求めている。そのため、分割したかたまりを 1 本ずつ順に送り、プロセス全体で同時に送れるのは 1 本までに直列化した（保存期間は 3〜100 日から選ぶ）。実際の送信の確認は、利用者の了解を得て、1 回ずつ試験的に行った。
- 外部への送信は、相手のサービスに利用者のファイルが渡る操作です。送り先の選択は利用者に任せ、チェックした送り先にだけ送る。「リンクを知っている人は閲覧可」という共有設定は、利用者に明示する。
- 費用: 各サービスには保存容量・転送量・API の割り当ての上限や、有料のプランがある。大容量の動画を送る前に、相手側の容量と課金の条件を確かめる。この記録では課金の発生する操作は行っていない。
- 認証の情報（クライアント ID、トークン、API の鍵）は、ファイルにも、ログにも、記録にも書かない。

### 実際に踏んだ落とし穴

- 送り先を書き出し先と同じ場所にすると、何も送られないのに「完了」になる、または「送信中」のまま終わらない。Drive と Frame.io の送り先を書き出し先と同じ場所にしていたのが原因で、送る前の検査で拒否するようにした（Drive の場合は、送り先が同期のマウント配下であることと、書き出し先と重ならないことを検査）。
- ギガファイル便は、2 かたまり目で失敗した。1 かたまり目の応答の `Set-Cookie` を、2 かたまり目以降のリクエストに載せていなかった。分割アップロードを模倣する連携では、全部のかたまりで Cookie を共有する。
- IRERU が `HTTP 403: error code: 1010` を返した。Cloudflare が、Python 標準の `urllib` の既定の名乗り（User-Agent）を弾いていた。通知の Webhook でも同じ形で再発した（GET は通るのに POST だけ 403）。外へ出す HTTP の呼び出しには、必ず User-Agent を明示する。
- IRERU が返す動画の URL が `localhost:3000` になっていた。相手側の環境変数が由来で、利用者に返すリンクが使えなかった。設定された本来のオリジンへ正規化し、履歴に残った古いリンクも表示時に直す。
- Drive の同期フォルダの最上位への書き込みが `Permission denied` になった。マイドライブの直下に書き込める形（API での直接アップロード）に変えた。
- Frame.io の API の取り違えがあった（`files` と `files/local_upload`、文字列の配列を辞書の配列として扱う、古い共有リクエストの形）。現行の API の仕様に合わせた。
- Frame.io のログインの戻り先は、ブラウザのリダイレクトで、独自のヘッダ（`X-CutSRT-Token`）を付けられない。そのため、戻り先のルートだけをトークン検査の外に置き、`state` の一致で守る。
- Adobe の資料どうしが食い違う: 実装ガイドは「Native App の資格情報には refresh_token が出ない」と書く一方、API リファレンスは更新の例を載せている。リダイレクト URI も「HTTPS 必須」と「Native App は HTTPS でなくてよい」の 2 通りが書かれている。実際に登録してログインして確かめるまでは確定とせず、両論を手順書に残した。新しく作るときも、どちらの場合も想定し、refresh_token が出ないときは再ログインを案内する作りにするのが安全である（推奨。実機での確認は無い）。
- Frame.io は、トークンの更新に成功しても `/accounts` が 401 のまま、という状態があり、原因は未確定です。診断は、読み取りだけの呼び出しで切り分ける。
- セキュリティの注意: 手元のサーバー（127.0.0.1）が OAuth の戻り先になる設計は、同じ機械の別のプロセスから戻り先へ偽の呼び出しをされうる。`state` の一致の検査で守る。待ち受けは必要なときだけ開く作りが望ましい（推奨。この記録では確認していない）。
- クラウドへの通信は、テストでは全部、偽の応答に差し替える。実際のサービスへの試験は、利用者の明示の了解を得て、1 件ずつ行う。

## 結果と今の状態

ギガファイル便は、単一のかたまり（73MB）の実送信に成功しました。1.34GB の送信は Cookie の問題で失敗し、修正後の再確認は残っています。Drive、Frame.io、IRERU は、模擬応答のテストと、一部の実機での確認にとどまり、実際のファイルを送って相手側でリンクを開くところまでは、確認が残っています。Frame.io の実ログインは、Adobe の開発者側の登録待ちで、一度も行っていません。
