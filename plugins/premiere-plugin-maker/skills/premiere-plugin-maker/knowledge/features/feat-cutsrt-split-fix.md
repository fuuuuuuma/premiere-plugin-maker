## 何をする機能か

字幕（SRT）を作ったあとで、「ここは 2 行に分けたい」「この 2 つは 1 つにしたい」「本文を直したい」「間違えた言葉を全部まとめて直したい」ときに使うタブです。テロップのタブの隣にあります。**直した字幕は別名で保存し、プロジェクトへ読み込み直せます**。

## 作り方

- **画面**: 直近に生成した SRT（またはファイルを選んだもの）を、番号・時刻・本文・操作ボタンの 4 つの固定の列で 1 行ずつ表示する。本文の列だけが伸び縮みし、長い文は「…」で省略して、全文は編集のときに確かめる。
- **純関数**: SRT の解析、直列化、分割の位置の決め方、キューの分割、結合は、画面にも Premiere にも触れない関数にした。状態を渡して新しい状態を返す形で、元の配列は書き換えない（「元に戻す」の記憶が汚れないため）。
- **ファイルの読み書きはサーバー**: UXP のパネルは、ファイル選択のダイアログを通さずに任意の場所を読み書きするのが苦手なので、読み込み・書き出しのルート（`/srt/read`・`/srt/write`）をサーバーに作った。`.srt` だけ、最大 10 MB、書き込みは「一時ファイルに書いて置き換える」方式。
- **分割の位置**: 本文の中に `/` を入れて指定するのを最優先にする（実行時に除去）。次に、入力欄のカーソル位置（`selectionStart`）、なければ中央。時間は前後の**文字数の比**で割り振る。`selectionStart` が取れない環境でも、`/` なら確実に指定できる。
- **改行の扱い**: キュー内の改行は、1 行の入力欄で編集できるように `⏎` と 1 対 1 で行き来させる（長さが同じなのでカーソル位置も一致する）。
- **書き出し**: 既定は `名前.edited.srt` の別名。サーバー側が `.edited-1`… の増殖を防ぎつつ衝突を避ける。上書きも選べる。
- **一括置換・削除・元に戻す**: 全キューが対象。検索語を入れた時点で「◯件が置換されます」と見せる。選択状態は、位置の番号でなくキューの実体の集合で持つ（分割・結合でずれない）。「元に戻す」は 4 つの操作（一括置換・削除・分割・結合）が 1 本の履歴を共有し、最大 20 件。別のファイルを読み込んだら履歴を捨てる。
- **再生**: このタブ自体は字幕の編集に専念する。聞き直しなど再生・停止が要る場面は、UXP に再生 API が無いため、パネル全体で CEP の再生ヘルパー経由になる（`feat-cutsrt-playback-helper`）。

## 使った API と道具

- UXP のパネル（HTML／CSS／JS）。ファイルの読み書きはサーバー経由。
- 純関数のテストは Node（画面の部分は要素の簡易スタブ）。
- CEP の再生ヘルパー（再生・停止）。

## つまずきと直し方

- **行が押しつぶされて、ボタンが本文に重なる**（33 キューを読み込んだとき）。親が縦並びで高さの上限（`max-height`）を超えると、UXP は行を中身より小さく縮める（実測で行の高さ 12px、中身 32px）。折り返しの設定の問題ではなかった。→ 行に `flex: 0 0 auto`（縮めない）を付け、あふれた分は親のスクロールに任せる。固定の列と `min-width: 0` と省略表示で 1 キュー 1 行にする。Chromium の下見では再現しにくいので、UXP 相当の弱い規則で下見する（`core-ui-rules`）。同じ現象は辞書の一覧と素材の検索結果でも起きた。
- **空の検索語・空にもマッチする条件で、全文が壊れる**。→ 空検索・壊れた正規表現・`a*` のような空にもマッチする条件は実行せず、エラーにする。
- **置換文字列の `$` が暴発する**（`$&` など）。→ 文字として扱う。正規表現をオンにしたときだけ `$1` の後方参照を許す。
- **全キューの削除で SRT が空になる**。→ 拒否する。
- **元に戻すの記憶が参照の共有で汚れる**。→ 純関数は元の配列を書き換えない。
- **別のファイルの内容を書き戻す事故**。→ 別のファイルを読み込んだら履歴を破棄する。
- **UXP で入力欄のカーソル位置が取れない環境がある**。→ `/` での指定を最優先にする。
- **画面を変えたら実機で確認する**。下見は Chromium の描画で、UXP の描画そのものではない。

## 結果と今の状態

- 純関数と画面の流れは自動テストで固定済み。押しつぶしの修正は実機の報告（スクリーンショット）を受けた直しで、Chromium での実測で確認した。
- 実機で「33 キューを読み込んで行が潰れず、ボタンが押せる」ことは、記録の時点では確認待ちだった。
