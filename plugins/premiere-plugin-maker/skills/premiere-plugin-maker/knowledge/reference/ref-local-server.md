## 仕様

UXP のパネルは、文字起こしや動画の処理のような重い仕事を自分では持てません。そこで、同じ PC の中に小さな HTTP サーバー（Python）を常駐させ、パネルが `fetch` で頼みます。Cut & SRT の作りを一般化したものが、キットの部品 local-server です。

**通信の決まり**

| 決まり | 内容 |
|---|---|
| 待ち受け | `127.0.0.1` だけ。外のホストから届く構成にしない。`0.0.0.0` と、IPv6 に解決され得る `localhost` の名前は避ける |
| 合言葉（token） | 起動のたびに新しく作る（例：16 バイトの乱数）。全部の道筋で `X-…-Token` ヘッダを調べ、違えば 403。比較は時間が一定の関数で |
| 握手のファイル（`server.json`） | 内容：pid・ポート・版・token・通信仕様の番号・一時フォルダ・サーバーの場所。パネルはこれを読んで接続する |
| 通信仕様の番号 | パネルとサーバーが共有する整数。食い違ったら接続せず、「同じ版に更新してください」と案内する |

**握手のファイルの書き方**

- 場所：Mac は `~/Library/Application Support/<アプリ名>/server.json`、Windows は `%APPDATA%\<アプリ名>\server.json`。
- 権限は 0600（本人だけ）。**待ち受けを始められた後にだけ**書く。一時ファイルに書いて `fsync` し、`os.replace` で原子的に置き換える。終了時は自分の pid の記録だけ消す。
- 読む側（パネル・MCP）は、所有者以外が読めるファイルは採用しない、中身（token が空でない・ポートが 1024〜65535・通信仕様が整数）を検査する、という約束にする。
- 一時フォルダは握手のファイルの `tmpDir` で受け渡す。サーバーは「その一時フォルダの下で、想定した拡張子」のファイルだけ読み書き・削除する。

**ジョブ（時間のかかる処理）**

- 開始：`POST /jobs/<種類>` → 202 と `jobId`。同時に動かすのは 1 本で、空き確認と登録を同じロックの中で行い、ふさがっていれば 409。
- 状態：`GET /jobs/<id>` → `status` は `queued`・`running`・`done`・`error`・`cancelled`、ほかに `percent`・`message`・`result`・`error`。
- **ジョブ自体が失敗しても、HTTP の応答は 200 で `{status:"error"}`** を返します。通信の層で先に例外にしてしまうと、ポーリングの層が「通信が切れた」と誤認するからです。
- 中止：`POST /jobs/<id>/cancel`。キャンセルは失敗と区別して表示する。
- **ポーリング**：最初の 5 回は 300ms、以降は 1500ms 間隔。通信の断は 3 回まで許す。起動の直後はサーバーよりパネルが先に立つので、接続の失敗は数秒おきに数回、自動でやり直す。

**設定**：変更のたびに（500ms ほどまとめて）全項目を保存する。秘密の値は応答に出さず、OS の保管庫に置く（部品 keychain）。

**常駐**

- Mac：launchd。`RunAtLoad` を真、`KeepAlive` は「正常終了以外で再起動」。起動の遅れを防ぐ `ThrottleInterval`（10 秒など）を付ける。**シェルの環境を引き継がないので、PATH と HOME を plist に書く。** 再起動は `launchctl kickstart -k gui/$(id -u)/<ラベル>`。
- Windows：タスク スケジューラ（`-AtLogOn`、`pythonw.exe`）。再起動の回数と間隔、時間制限なし、バッテリでも動かす、多重起動なし。`pythonw` は標準出力がないので、ログは自前でファイルに付け替える。サインイン時の自動起動そのものは、実機で確かめていません。
- 起動後は、launchd の pid と握手のファイルの pid が一致するか、`POST /ping` が `ok` を返すか、を数回確かめて「動いた」とします。

**版ごとの runtime**

- サーバーの本体は `runtime/<版>/` に置き、使用中の版を `current.json` に書く。切り替えは原子的に行い、失敗したら元に戻す（ロールバック）。
- **同じ版の runtime が既にあると、検証だけして上書きしません。** 開発中に直しても、版を上げるか先に削除しないと反映されず、古いサーバーが動き続けます（core-versioning-release）。

## 例

起動の流れと、パネル側の接続の流れ：

```
サーバー: token を作る → 127.0.0.1:ポート で待ち受け成功 → server.json（0600）を原子的に書く
パネル : server.json を読む → 通信仕様の番号を比べる → X-…-Token を付けて呼ぶ
        → 403 ならサーバーが再起動して token が変わったと見て、server.json を 1 回だけ読み直して再試行
```

パネルの UXP の manifest では、`requiredPermissions.network.domains` を `"all"` にします（127.0.0.1 の個別指定では `fetch` 自体が起きなかった記録があるため。Windows でも `all` で接続を確認）。動作を確かめてから絞ります。

## 注意

- **ログが膨らむ**：ポーリングの 1 回ごとをログに記録すると、数 MB〜数十 MB に育ちます（パネル側のログが 20MB・14 万行に育った例）。ポーリングは記録せず、一定の大きさで古いものを 1 世代だけ残して作り直します。launchd のログは稼働中に `truncate` せず、`mv` してから再起動します。
- **PATH の違い**：Finder・launchd・常駐から起動した処理は、PATH が最小です。ターミナルでは動くのに、常駐のサーバーが ffmpeg を見つけられない症状の原因は、ほぼこれです。既知の場所（`/opt/homebrew/bin` など）を探す候補に足し、実際に起動して確かめます。
- **古い握手のファイル**：開発中のリポジトリから起動した道具が、隣に残った古い握手のファイルを読んで 403 を返し続ける事故がありました（MCP の記録。ref-mcp）。握手のファイルの探し場所は、「環境変数 → アプリのデータフォルダの `server.json` → 隣のファイル」の順にします。
- 秘密の値は、`settings` に平文で置かず保管庫へ。AI にログや設定を見せるときは、鍵の名前で判定して「設定済みかどうか」の真偽値に置き換えます。
- OneDrive の同期対象や、Windows Defender の誤検知に注意（platform-windows）。
- Windows のタスク スケジューラの権限、Windows の `faster-whisper` の速さなどは、実機の確認が限られています。
